# 测试方法工具箱

本文件是测试方法论参考库，供 test-architect 和 test-designer 在需要时查阅。

---

## 1. 测试策略：测什么、怎么测

**核心思路：** 测试不是"测完所有东西"，而是根据质量目标和风险，在有限时间里做**刚刚好的测试**。

**制定策略时回答三个问题：**
1. 质量目标是什么？（产品最不能出错的地方在哪）
2. 风险在哪里？（哪些地方最容易出错、出错了影响最大）
3. 资源和时间有多少？（决定测多深、测多广）

**策略五要素：**
- 测试对象与范围 — 哪些模块/功能纳入测试
- 测试目标 — 通过测试要达成的质量标准
- 测试重点与难点 — 高风险、高复杂度区域加大投入
- 测试深度与广度 — 重点区域深测，非重点区域浅测
- 测试活动顺序 — 先测什么、后测什么

**四步制定法：**
1. 明确质量目标 → 用质量模型定目标，目标-行为-评估形成闭环
2. 风险分析 → 识别可能阻塞测试的风险，基于风险调整投入
3. 适配研发流程 → 测试活动对齐开发节奏（开发设计时做测试分析，开发集成时做测试执行）
4. 测试分层 → 将相同目的的测试分组，每层目标 SMART 化

## 2. 测试方法车轮图

**关系链：** 质量属性 → 测试类型 → 测试方法

即：你要测产品哪个质量维度（功能性？可靠性？）→ 对应哪种测试类型（功能测试？稳定性测试？）→ 用哪些方法（等价类？边界值？压力测试？）

**两个用途：**
- 保证全面性：对照六属性检查是否有遗漏
- 确定深度：某属性用的方法越多，测得越深

**六质量属性速查：**

| 属性 | 关注点 | 常见测试类型 |
|------|--------|-------------|
| 功能性 | 正确性、安全性、兼容性 | 功能测试、安全测试、兼容性测试 |
| 可靠性 | 成熟性、容错性、可恢复性 | 稳定性测试、异常测试、恢复测试 |
| 易用性 | 易理解、易操作、界面 | 用户体验测试、帮助文档测试 |
| 效率 | 时间特性、资源利用 | 性能测试、压力测试、容量测试 |
| 可维护性 | 易分析、易修改、可测试 | 代码审查、单元测试 |
| 可移植性 | 适应性、易安装、共存 | 平台兼容测试、安装测试 |

## 3. 测试点 ≠ 测试用例

- **测试分析** → 得到**测试点**，是**发现性**过程——不同测试者看到的测试点差异不大
- **测试设计** → 得到**测试用例**，是**创造性**过程——加工测试点（组合、拆分、选数据），不同测试者产出的用例千差万别

一个测试点可以展开为多个测试用例（不同数据、不同路径、不同场景）。

**测试点四分类（选模依据）：**

| 类型 | 怎么认 | 怎么建模 | 怎么设计用例 |
|------|--------|---------|-------------|
| 流程类 | 有步骤分支，不同输入走不同路径 | 流程图/状态机 | 路径分析法 |
| 参数类 | 参数值有限，不同值不同处理 | 输入-输出表 | 覆盖每行 |
| 数据类 | 取值范围，范围内处理相同 | 等价类表 | 等价类+边界值 |
| 组合类 | 多因素需一起考虑 | 因子表+流程图 | 正交分析 |

## 4. 四步测试设计法

```
建模 → 基础用例 → 数据补充 → 扩展
```

四步法从四个维度保证完备：**模型**（结构）→ **覆盖**（基础用例）→ **深度**（数据补充）→ **广度**（扩展）。

---

### 4.0 测试点分类（建模前置）

在建模前，先判断每个测试点属于哪类，类型决定后续选什么模型、用什么设计方法。

| 类型 | 特征 | 建模方式 | 设计方法 |
|------|------|---------|---------|
| 流程类 | 有步骤和分支，不同输入走不同路径，可绘成流程图 | 流程图 / 状态机图 | 路径分析法 |
| 参数类 | 参数取值有限，不同值对应不同处理或响应 | 输入-输出表 | 逐行覆盖 |
| 数据类 | 数据为取值范围，范围内处理相同 | 等价类分析表 | 等价类 + 边界值 |
| 组合类 | 多因素叠加影响结果 | 因子表 + 流程图 | 正交分析 |

**区分口诀：**
- 流程类 = 能画"输入→判断→动作→…"的图
- 参数类 vs 数据类 = 值是离散且每个值处理不同 → 参数类；值是连续范围且处理相同 → 数据类
- 组合类 = ≥2 个独立因素互相影响

---

### 4.1 建模

将需求转化为可视化模型，为后续设计提供结构。

**执行步骤：**
1. 识别主流程、分支流程及所有测试点
2. 对每个测试点分类（流程/参数/数据/组合）
3. 按类型建模：
   - 流程类 → 画业务流程图或状态机图（Mermaid），与需求方确认流程正确性
   - 参数类 → 建输入-输出表（参数 + 取值 + 约束 + 预期输出）
   - 数据类 → 建等价类分析表（条件 + 有效等价类 + 无效等价类）
   - 组合类 → 建因子表（因子 + 各水平），必要时叠加流程图
4. 提取输入参数、前置条件、后置条件、约束关系

**产出：** 可视化模型 + 关键路径/关键输入输出组合列表。

---

### 4.2 基础用例

基于模型产出最小覆盖用例集，确保每条路径/每行/每个等价类至少一条用例。

#### 流程类 — 路径分析法

基于流程图/状态机列出路径集合，选择覆盖策略：

| 策略 | 做法 | 覆盖力 | 用例量 | 适用场景 |
|------|------|--------|--------|---------|
| 语句覆盖 | 覆盖所有判定和过程的最小路径集 | 弱 | 少 | 次要功能、单元测试初筛 |
| 分支覆盖 | 每个判定的 True/False 至少各一次 | 中 | 中 | 集成/系统测试常规 |
| 最小线性无关覆盖 | 每个路径片段至少一次，路径数 = 判定数+1 或 边数-节点数+2 | 较强 | 可控 | **推荐：** 集成/系统测试首选 |
| 全覆盖 | 所有可能路径 | 最强 | 多 | 核心高风险流程 |

**选用建议：**
- 单元测试：语句覆盖或分支覆盖
- 集成/系统测试：最小线性无关覆盖（常规）+ 全覆盖（高风险）
- 次要功能：语句覆盖或分支覆盖即可
- 不建议：全线全覆盖（代价大）或全线语句覆盖（太弱）

每条选定的路径对应至少一条基础用例。

#### 参数类 — 输入-输出表覆盖

考虑参数间约束后，对输入-输出表的**每一行**设计一条用例（100% 覆盖）。

#### 数据类

等价类分析表已建好，具体数据选取在下一步（数据补充）用边界值确定。

#### 组合类 — 正交分析

用正交表覆盖多因子多水平组合，再根据约束剔除无效组合。

#### 通用原则

- 先覆盖主流程再覆盖分支流程
- 每个逻辑判断的 True/False 至少各覆盖一次
- 用例步骤清晰、预期结果明确

---

### 4.3 数据补充

在基础用例之上注入具体数据，挖掘边界和组合的深层缺陷。

**技术方法：**

| 方法 | 做什么 | 示例 |
|------|--------|------|
| 等价类划分 | 有效等价类（符合规则）+ 无效等价类（违反规则） | 有效：1~100；无效：0、101、字母 |
| 边界值分析 | 取刚好等于、刚刚大于、刚刚小于边界的值 | 边界 1 和 100 → 测 0、1、2、99、100、101 |
| 判定表 | 多条件组合时，列出所有条件桩和动作桩 | 条件 A×B×C → 2³=8 种组合 |

**执行：**
1. 对每个输入参数做等价类和边界值分析
2. 对复杂逻辑组合用判定表
3. 补充负向测试用例（无效数据 + 边界数据）

---

### 4.4 扩展

模型覆盖不到的地方，用经验和非功能视角补充。

**错误推测：** 基于经验猜 bug 高发点 — 特殊字符、空值、重复提交、网络中断、超时、并发冲突、异常输入。

**非功能测试：** 用车轮图六属性扫描遗漏
- 兼容性：浏览器、系统版本、分辨率
- 性能：大数据量、并发、响应时间
- 安全性：越权、注入、敏感信息泄露
- 易用性：提示清晰度、操作路径合理性

**探索性测试：** 模拟真实使用场景，适度发散探索，发现脚本外的风险。

## 5. 分层测试（V 模型）

```
单元测试 → 集成测试 → 系统测试 → 验收测试
```

| 层次 | 测什么 | 谁来做 |
|------|--------|--------|
| 单元测试 | 函数/方法级正确性 | 开发 |
| 集成测试 | 模块间接口正确性 | 开发/测试 |
| 系统测试 | 功能+非功能全貌 | 测试 |
| 验收测试 | 用户业务需求 | 产品/用户 |

**设计原则：**
- 每层测试目标必须 SMART（具体、可衡量、可获得、相关、有时限）
- 根据产品特点裁剪层次（如集成层拆成模块集成+端到端集成）
- 分配用例时标明所属层次

## 6. 风险分析

**三步骤：**

1. **识别风险** — 问"测这个需要什么条件？哪些条件不满足？"。可从需求、设计、流程、历史四个维度检查
2. **评估风险** — 从发生频率和影响程度两维评估，正交出高/中/低优先级
3. **应对风险** — 回避（换个方法）、转移（让人协助）、减轻（降优先级先不管）、接受（知道了继续干）

**老功能分析：**
- 差异性分析：找出新老版本在需求、设计、平台、实现上的差异，据此判断测什么
- 历史测试分析：看历史缺陷分布、测试方法覆盖情况，决定老功能的测试深度

---

## 7. 测试覆盖度评估

| 维度 | 指标 | 目标 |
|------|------|------|
| 需求覆盖 | 已验证需求数 / 需求总数 | 100% |
| 路径覆盖 | 已测路径 / 可执行路径总数 | 最小线性无关覆盖（基本） |
| 测试方法覆盖 | 已用方法 / 车轮图方法总数 | 按质量目标定，重点区域覆盖率更高 |

**用法：** 用例设计完成后，回头对照评估是否达到覆盖目标。

---

## 8. 缺陷分析

持续关注：缺陷密度（每模块/每千行）、修复率、缺陷趋势（上升/下降）、缺陷年龄（存活多久）、触发因素分布。

用于：评估测试效果、调整测试策略、决定是否加测/减测。
